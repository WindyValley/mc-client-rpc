# 测试策略

本文说明 mc-client-rpc 怎么测、哪些能纯单测、哪些必须真机，以及真机自动化的组织方式。

## 分层测试思路

按「是否依赖 Minecraft runtime」把代码分成两类，分别用不同手段验证：

| 层 | 代表类 | 依赖 MC | 测试方式 |
|----|--------|---------|---------|
| 协议层 | `protocol/RpcDispatcher` | 否 | 纯 JUnit |
| 网络层 | `protocol/RpcServer` | 部分 | 结构审查 + 真机 |
| 操控层 | `client/ClientPlayerController` | 是 | 真机自动化 |
| 装配 / 入口 | `ClientRpcService`、`McClientRpc`、平台入口 | 是 | 真机 + 编译验证 |

核心原则：**能脱离 MC 的逻辑尽量做成可纯测；离不开 MC 的行为不在单测里硬造，而是用真机自动化覆盖。**

## 单元测试（协议层）

`RpcDispatcher` 刻意不引用任何 MC 类型，输入输出都是文本/JSON，因此可纯 JUnit 验证：

- 合法请求的解析与路由；
- `result` 包装；
- 错误码：
  - 非法 JSON → -32700；
  - 缺 `method` → -32600；
  - 未知方法 → -32601；
  - handler 抛异常 → -32603；
- handler 之间的异常隔离（一个 handler 抛错不影响分发器继续工作）。

跑：

```bash
./gradlew test
```

## 为什么操控层不用 Mock 硬造

`ClientPlayerController` 的每个动作都要访问真实的玩家实体、世界、网络连接和游戏循环，且关键正确性（服务端是否看到动作、攻击是否命中、触摸到怪的反应）只能在真实客户端 + 真实服务器上体现。

用 Mock 伪造这些对象，测的是 Mock 的行为，不是游戏的真实反应，容易给出假信心。因此这一层**明确移交真机验证**，而不是加一个庞大的 Mock 套件。

## 真机自动化

真机验证用一个**独立 Minecraft 客户端 + 专用服务器**，脚本驱动真实玩家。

### 三条通道

| 通道 | 端口 | 作用 |
|------|------|------|
| mc-client-rpc JSON-RPC | 25586 | 操控客户端玩家（走/打/跳/视角/命令）|
| Minecraft RCON（被依赖方）| 25575 | 服务器管理：召唤、清场、改规则 |
| 被测系统调试探针（使用方，可选；非本框架通道）| — | 由使用本框架的上层工程自行提供 |

### 自包含时序

每个真机脚本在**单个脚本内**完成全部等待、轮询与断言，只在终端跑一次，读最终结果：

- 客户端启动 / 连接：用 `scripts/launch_and_connect.py`，内部等 RPC 就绪、标题屏连续稳定、连接进世界；
- 慢等待（走近、攻击命中、怪物反应）用脚本内 `time.sleep` + 轮询，不在工具调用之间靠外部循环；
- 每步带断言，失败即停并指出卡在哪步；
- 退出码：0 通过，非 0 失败。

### 清理纪律

- 测试脚本用 try/finally 保证清理召唤实体、恢复游戏规则（如 `doMobSpawning`）。
- **客户端测完立即退出**，不留到下一轮（通过找 25586 LISTENING 的 PID 并终止）。
- 只杀客户端，测试服务器保留运行。

### 脚本目录约定

- 通用驱动与工具：`scripts/`（`combat_loop_test.py`、`rcon.py`、`launch_and_connect.py`、`kill_mc_java.py`）。
- 不依赖 MC 的脚本逻辑用内嵌假 RPC server 做确定性回归：`scripts/test_launch_and_connect.py`
  覆盖启动就绪判据（标题屏连续稳定、引导屏盖回重切）与 Fabric 进世界瞬间连接重置/空响应容错，
  跑真机前可先 `python scripts/test_launch_and_connect.py` 快速验证（需先退出占用 25586 的真实客户端）。
- 一次性 / 调试脚本：`scripts/_temp/`（git 已忽略，不入库）。
- 脚本写成独立 `.py` 文件，终端只跑 `python xxx.py`，不内联复杂管道。

## 判据以服务端权威为准

真机判定时注意：

- 攻击返回串里的目标血量是**客户端即时预测**，命中以**服务端**血量/玩家实际掉血为准；
- 客户端本地血量在发包后不立即更新；
- 「玩家没掉血」要区分是真被拦住，还是怪尚未进入攻击条件——必要时用「打一拳触发反击」做双向对照。

## 已实际覆盖的路径

本框架已在真机上驱动过典型的行为自动化场景，覆盖：攻击命中、走位、跳跃、同族示警、脱战恢复等路径。这些验证反过来也证明了框架自身操控能力（真实输入、发包、状态读取）的可靠性。具体使用实例见根 README。

## 建议的后续测试增强

- 为操控层补少量「可脱离具体世界」的纯逻辑测试（如参数解析、门槛值计算），把能抽出来的判定从 MC 依赖中隔离；
- 关键回归路径（导航链、攻击链）沉淀为可重复运行的标准脚本。
